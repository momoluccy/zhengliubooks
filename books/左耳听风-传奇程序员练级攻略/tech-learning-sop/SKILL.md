# 系统学习技术模板（六维度SOP）

## R — 原文 (Reading)

> "系统学习技术的模板包含六个维度：学习技术的背景、初衷、要达到的目标或要解决的问题。学习技术的优势和劣势。学习技术的适用场景。学习技术的核心组成部分和关键点。学习技术的底层原理和关键实现。学习技术与已有实现的对比。如果按照这个模板来学习一项技术，入门阶段就会超过很多人，也更容易学到精髓。"
>
> — 陈皓, 第8章 高效学习

---

## I — 方法论骨架 (Interpretation)

这是一套可直接执行的六维度技术学习检查清单。大多数人的技术学习是"看官方文档→跑Hello World→照着教程做"的三板斧，学完只会用但不知道为什么。六维度SOP要求你在学习任何技术时都覆盖六个方面：

1. **背景**：这项技术为什么被创造出来？它要解决什么问题？诞生于什么时代背景？了解背景让你理解"它的设计约束是什么"，从而判断"这些约束今天还适用吗"。
2. **优劣**：它擅长什么、不擅长什么？没有万能的技术，知道劣势比知道优势更重要——因为劣势决定了"什么时候不该用它"。
3. **适用场景**：它在什么场景下表现最好？什么场景下表现差？这个维度直接服务于技术选型决策——不是为了用而用，而是为了场景而选。
4. **核心**：它的核心组件和关键概念是什么？抓住20%的关键点就能理解80%的行为。这个维度帮你快速建立心智模型。
5. **底层原理**：它的核心机制是怎么实现的？底层用了什么基础理论？这一步把"会用"升级为"理解"——当你遇到文档没覆盖的edge case时，底层原理是你唯一的指南针。
6. **对比**：它和同类技术相比有什么不同？对比产生洞察——知道"A比B好在哪"本质上是在理解设计trade-off。

六维度的顺序有讲究：先理解"为什么存在"（背景），再知道"好在哪里/差在哪里"（优劣+场景），然后抓住"核心是什么"（核心），深入"底层怎么运作"（原理），最后"和同类比比看"（对比）。先攻核心（第4点），其他顺藤摸瓜。

## A1 — 书中的应用 (Past Application)

### 案例 1: 从Java到C++到C的逆向学习 — 六维度的自然实践
- **问题**: 作者学习Java时发现书中涉及C++知识，学C++时又发现需要C的基础，需要找到系统的方法来贯通三种语言。
- **方法论的使用**: 虽然当时没有显式使用六维度模板，但学习路径自然覆盖了六维度——背景（每种语言为什么被创造）、优劣（Java的跨平台vs C的效率）、核心（C的指针/内存管理、C++的面向对象、Java的GC）、原理（JVM如何实现跨平台）、对比（三者之间的演进关系）。
- **结论**: 融会贯通的关键不是"学了三种语言"，而是理解了它们之间的"为什么"和"怎么来的"——这正是六维度SOP的核心思想。
- **结果**: "C-C++-Java"整条学习线路融会贯通，对未来的技术成长有非常大的帮助。

### 案例 2: 帮助饿了么设计异地多活方案 — 从核心到原理的实践
- **问题**: 饿了么面临高并发外卖订单的系统压力，需要设计分布式架构方案。
- **方法论的使用**: 作者在解决这个实际问题时，隐含使用了六维度的第4和第5维度——抓住"异地多活"的核心组件（数据同步、流量调度、一致性保障），理解底层原理（CAP理论、一致性协议），然后才能设计出可行的方案。
- **结论**: 理解底层原理是从"会用技术"到"能设计系统"的关键跨越。
- **结果**: 异地多活方案成功撑住了全网外卖订单的高峰流量。

### 案例 3: 2016年选择可观测性作为创业方向 — 背景+场景+对比的综合判断
- **问题**: 创业需要选择产品方向，需要评估可观测性这个技术领域是否值得投入。
- **方法论的使用**: 运用了六维度中的"背景"（可观测性为什么被创造——分布式系统的复杂性需要全新的监控思路）、"场景"（分布式系统的可观测性需求在国外已经验证过）、"对比"（与国内已有的监控方案对比，发现差距）来做判断。
- **结论**: 国内市场对可观测性的需求还没有被满足，而国外的实践已经证明了这个方向的价值。
- **结果**: 创业做可观测性产品，后来在国内走热，验证了基于六维度分析的技术方向判断。

## A2 — 触发场景 (Future Trigger)

### 用户会在什么情境下需要这个 skill?

1. 用户说"我想学Rust/Kubernetes/Golang/某框架"但不知道从哪里入手——需要六维度SOP给出系统学习路线。
2. 用户在工作中需要快速评估一项新技术是否适合当前项目——需要快速覆盖六维度中的"背景+优劣+场景+对比"四个维度来做选型判断。
3. 用户已经会使用某项技术但感觉"只是会用，不理解原理"——需要补强六维度中的"核心+原理"两个维度。
4. 用户需要向团队或老板推荐采用某项新技术——需要六维度的完整分析来支撑推荐理由。

### 语言信号 (用户的话里出现这些就应激活)

- "我想学X，怎么系统学习/怎么入门"
- "我该怎么评估/分析这项技术"
- "这项技术适合什么场景"
- "X和Y到底该选哪个"
- "我会用X但不知道底层原理"
- "怎么快速掌握一项新技术"

### 与相邻 skill 的区分

- 与 `deep-learning-trio` 的区别: 本skill回答"学什么"（六维度检查清单），deep-learning-trio 回答"怎么学"（采集→缝合→转换的流程）。典型组合：用本skill确定要学的内容，用 deep-learning-trio 的方法来消化。本skill的六个维度是 deep-learning-trio "采集"环节的信息输入清单。
- 与 `five-step-thinking` 的区别: 本skill是技术学习SOP，给出学什么和按什么顺序学；five-step-thinking 是通用思考框架，用于评判信息可信度。本skill第六步"对比"中的逻辑分析会用到 five-step-thinking 的因果检验方法。
- 与 `competency-leap` 的区别: 本skill是微观的"如何系统学习一项具体技术"，competency-leap 是宏观的"竞争力发展的四阶段路径"。本skill是 competency-leap 第二步"知识"和第三步"技能"中可用的工具之一。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **确定目标技术并快速填充六维度 — "画一张六维度的速写"**
   - 按顺序快速填写：背景（为什么存在）→ 优劣（强项和弱项）→ 场景（适合/不适合）→ 核心（20%关键概念）→ 原理（底层机制）→ 对比（与同类技术的差异）。
   - 完成标准: 六个维度每个至少有一句话的回答。如果某个维度暂时无法回答，标注为"待深入"而非跳过。
   - 判停条件: 如果用户只是做快速选型评估（而非深度学习），只需完成前四维度（背景+优劣+场景+对比）即可给出初步判断。
   - 输出格式:
     ```
     ## [技术名称] 六维度速写
     | 维度 | 回答 | 深度 |
     |------|------|------|
     | 背景 | （为什么被创造，解决什么问题） | 一句话 |
     | 优劣 | 强项：…；弱项：… | 各1-2条 |
     | 场景 | 适合：…；不适合：… | 各1-2条 |
     | 核心 | 3-5个关键概念 | 列举 |
     | 原理 | 底层机制 | 一段话 |
     | 对比 | vs [竞品A/B] 的关键差异 | 2-3条 |
     ```

   ⏸️ **检查点**: 六维度速写完成后，暂停向用户确认：各维度的回答是否准确？是否有遗漏的重要方面？用户当前的需求是"快速选型"还是"深度学习"——若是前者，可直接跳到步骤3。

2. **重点攻克核心与原理 — "先攻核心第4点，其他顺藤摸瓜"**
   - 从第四维度"核心"切入，抓住该技术最重要的3-5个关键概念/组件，深入理解每个概念的工作机制。
   - 然后进入第五维度"原理"，理解这些核心概念的底层实现——用了什么基础理论？关键算法是什么？设计约束是什么？
   - 完成标准: 能用自己的话解释每个核心概念的工作原理，并能回答"为什么这样设计"。
   - 输出格式:
     ```
     ## 核心概念深入
     ### 概念1: [名称]
     - **作用**: …
     - **工作机制**: …
     - **设计原因**: …

     ### 概念2: [名称]
     …（重复上述结构）
     ```

3. **对比验证与场景匹配 — "和同类比比看，是否适合我的场景"**
   - 找到2-3个同类/竞品技术，做对比分析：各自的设计目标、优劣、适用场景的差异。
   - 将分析结果与用户的实际场景匹配：你的场景特征是什么？哪项技术的优势最匹配？劣势是否可接受？
   - 完成标准: 输出一张"技术X vs 技术Y"的对比表，并给出基于用户场景的推荐结论。如果是为了学习而非选型，则完成"能向他人解释这项技术与竞品的区别"即可。
   - 输出格式:
     ```
     ## 技术对比表
     | 对比维度 | [技术A] | [技术B] | [技术C] |
     |----------|---------|---------|---------|
     | 设计目标 | … | … | … |
     | 核心优势 | … | … | … |
     | 主要劣势 | … | … | … |
     | 适用场景 | … | … | … |
     | 社区/生态 | … | … | … |

     **场景匹配结论**:
     - 用户场景: …
     - 推荐技术: …
     - 推荐理由: …
     ```

## B — 边界 (Boundary)

### 不要在以下情况使用此 skill

- **纯操作指南需求**: 用户问"怎么安装Docker""怎么配置Nginx"这类只需照做的问题，六维度SOP太重了——直接给操作步骤。
- **紧急排查问题**: 线上故障排查需要快速定位和修复，不是系统学习技术的时候。
- **已有明确学习路径的领域**: 如果用户已经有该领域的系统学习路径（如大学课程、认证考试大纲），不必强套六维度。

### 作者在书中警告的失败模式

- **技术平台锁定陷阱 (ce02)**: 将自身竞争力建立在某个特定平台的API上。"将自身核心竞争力建立在某个特定平台、框架或中间件的专用API上，而非底层原理。"——六维度SOP的第5维度"原理"正是为了对抗这个陷阱。如果只学API而不学原理，就是在建空中楼阁。
- **盲目追逐新技术 (ce11)**: 看到每个新技术都想深入学一遍。"看到每个新技术都想深入学一遍，精力分散在十几个方向上，每个都是浅尝辄止。"——六维度SOP的第一维度"背景"和第三维度"场景"可以帮助判断"这项技术是否值得我现在学"。如果背景表明它解决的问题你不会遇到，或者适用场景与你的工作无关，就可以跳过。
- **迷信标准答案 (ce04)**: 把技术学习简化为"背API、记语法"。"思维被'标准答案'固化，无法进行工程化的思考。"——六维度SOP的第2维度"优劣"和第6维度"对比"正是为了打破"某个技术就是标准答案"的思维定式。

### 作者的盲点 / 时代局限

- 六维度SOP假设每项技术都有足够的文档和资料来填充六个维度，但对于一些新兴技术或小众工具，资料可能不足以支撑完整的六维度分析。
- 模板偏重于"理解"维度（背景、原理、对比），对"实践"维度的指导较弱。用户可能完成了六维度分析但仍然不会写代码。这一点需要与 deep-learning-trio 的"转换"环节配合使用。
- "先攻核心第4点"的策略对于某些技术可能不适用——有些技术的核心概念（如Rust的所有权系统）在没有理解背景和原理的情况下很难直接攻克。

### 容易混淆的邻近方法论

- "官方文档阅读法"通常只覆盖了六维度中的"核心"和部分"原理"，缺少背景、优劣、场景、对比四个维度。
- "技术雷达评估"（如ThoughtWorks Technology Radar）主要覆盖六维度中的"优劣"和"场景"，是一张简化版的技术评估清单。
- "比较阅读法"（同时学习多本教材）主要服务于六维度中的"对比"维度，但不提供完整的六维度框架。

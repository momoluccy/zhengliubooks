# 技术领导力四支柱模型

## R — 原文 (Reading)

> 技术领导力不是管理职位，而是通过四个支柱建立的真正影响力：吃透基础技术，提高学习能力，坚持做正确的事，高标准要求自己。永远编程——不写代码，你就对技术细节不敏感，无法提供面向实践的技术决策和解决方案。
>
> — 陈皓，第17章 技术领导力

---

## I — 方法论骨架 (Interpretation)

这个模型将"技术领导力"拆解为四个独立但互相支撑的支柱，缺一不可：

**支柱一：吃透基础技术。** 基础技术是所有上层技术的地基，包括C语言/系统编程、TCP/IP网络原理、数据库内部机制、操作系统原理。这些知识不会过时，掌握了它们就能快速理解任何新技术的底层逻辑。不掌握基础的技术管理者做出的决策往往脱离实际。

**支柱二：提高学习能力。** 技术更新速度极快，领导力的持续性取决于学习能力的强弱。具体方法包括：订阅一手信息源（论文、官方博客、开源项目源码）、与高手交流（找Principal级别以上的工程师切磋）、使用系统学习模板（六维度SOP）。学习能力本身就是一种可以训练的元技能。

**支柱三：坚持做正确的事。** 在团队中推动代码审查、自动化测试、技术分享、CI/CD等"正确但可能有摩擦"的实践。不因为短期压力或团队惰性就妥协技术标准。这需要勇气——作者甚至说"等着被开除"。

**支柱四：高标准要求自己。** 定期给自己打分（10分制你打几分？），培养技术嗅觉（能闻到代码的味道），坚持每周编程。这个支柱的独特之处在于它是自我驱动的——不是为了给别人看，而是为了维持自己的技术敏感度。

四个支柱的关系是：基础技术提供判断力，学习能力提供成长速度，做正确的事提供影响力，高标准提供持续性。其中最容易忽略的是第四个——很多技术管理者停止编码后，前三个支柱也会逐渐瓦解。

## A1 — 书中的应用 (Past Application)

### 案例 1: 实习时被老板反问"这是做技术的人该有的态度吗"
- **问题**: 作者实习时被安排研究Java内存映射技术（MappedByteBuffer），觉得用普通Reader就够了，被老板严厉反问。
- **方法论的使用**: 这个事件直接对应"支柱四：高标准要求自己"。老板的反问让作者意识到，技术人不能只满足于"能用"，而要追求"最优解"。从此开始深入研究内存映射的底层原理，从Linux到JVM全面了解。
- **结论**: 高标准不是天生的，是在被"打脸"后建立起来的思维习惯。一旦建立了高标准，就会自动应用于所有后续工作。
- **结果**: 这句话成为作者职业生涯的转折点，激励他不断探索技术底层原理，养成了对技术精益求精的态度，最终成为对工程质量要求极高的技术专家。

### 案例 2: 在亚马逊与Principal SDE级别以上工程师交流
- **问题**: 作者需要在亚马逊这样的顶尖技术公司快速提升自己的技术思维层级。
- **方法论的使用**: 这直接对应"支柱二：提高学习能力"。作者遵循前辈建议，主动与美国Principal SDE级别以上的资深工程师交流。不论交流什么话题都能从中收获，因为高手的思维方式本身就是一种信息密度极高的学习资源。
- **结论**: 找高手切磋是提升技能的捷径。与比自己强的人交流，即使不讨论技术细节，也能从他们的思维模式中受益。
- **结果**: 技术思维有了质的提升，验证了"找高手切磋是提升技能的捷径"的方法论。

### 案例 3: 代码写得太烂被定性为"不适合写代码"
- **问题**: 作者早年因代码质量差被定性为不适合编程，差点因此离开技术道路。
- **方法论的使用**: 这个教训同时涉及"支柱一（吃透基础技术）"和"支柱四（高标准要求自己）"。被定性为"不适合写代码"的痛苦经历，让作者意识到光"能写代码"不够，必须写出高质量代码，而这需要深入理解底层原理。
- **结论**: 技术领导力的起点不是"管人"的能力，而是自己先成为技术过硬的人。被批评不可怕，可怕的是被批评后不改变。
- **结果**: 养成了对工作极其严谨的习惯，形成了高标准要求自己的技术思维，从"不适合写代码"到成为技术领导力的倡导者。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. **刚被提升为Tech Lead** — 用户刚从开发岗晋升为技术负责人，之前没有管理经验，问"怎么建立团队对我的信任"。
2. **管理后不写代码** — 用户做技术管理几年后，发现自己越来越不写代码，开始担心"脱离技术"但不知道如何平衡。
3. **团队技术标准低** — 用户作为技术负责人，对团队的代码质量和工程实践不满意，想推动提升但遇到阻力。
4. **想成为技术专家而非管理者** — 用户明确不想走管理路线，但想在技术路线上建立影响力（如成为Staff/Principal Engineer）。
5. **创业CTO困境** — 用户作为创业公司CTO，既要做管理又要保持技术能力，感到力不从心。

### 语言信号 (用户的话里出现这些就应激活)

- "刚当上技术Leader，怎么建立威信"
- "做管理后还要不要写代码"
- "团队对技术方案没有判断力"
- "怎么保持技术敏感度"
- "我想走技术路线不走管理路线"
- "怎么在团队中推动技术最佳实践"

### 与相邻 skill 的区分

- 与 `competency-leap` 的区别: competency-leap 是"认知→知识→技能→领导力"的完整四步路径，本skill只聚焦第四步"领导力"的具体建设方法（四个支柱）。前者是全局路线图，后者是终局的具体施工方案。
- 与 `do-right-things` 的区别: do-right-things 是一个独立的决策框架（五条标准检验某件事该不该做），本skill的"支柱三（坚持做正确的事）"只是四个支柱中的一个。前者可以单独使用，后者是更完整的领导力体系。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **诊断四个支柱的当前状态**
   - 让用户对四个支柱分别自评（1-10分）：(a) 基础技术掌握程度、(b) 学习能力强度、(c) 在团队中推动正确之事的频率、(d) 自我标准的高低和编码频率
   - 完成标准: 四个支柱都有明确的评分，识别出最薄弱的1-2个支柱
   - 输出格式:
     ```
     ## 技术领导力四支柱诊断
     | 支柱 | 自评分(1-10) | 状态 | 关键差距 |
     |------|-------------|------|----------|
     | 一：吃透基础技术 | ? | 🟢≥7 / 🟡4-6 / 🔴≤3 | … |
     | 二：提高学习能力 | ? | 🟢≥7 / 🟡4-6 / 🔴≤3 | … |
     | 三：坚持做正确的事 | ? | 🟢≥7 / 🟡4-6 / 🔴≤3 | … |
     | 四：高标准要求自己 | ? | 🟢≥7 / 🟡4-6 / 🔴≤3 | … |
     **最薄弱支柱**: [支柱名称]，得分: [X]/10
     ```

   ⏸️ **检查点**: 四支柱评分完成后，暂停向用户确认：评分是否真实反映了现状？是否存在自我高估（Dunning-Kruger效应）？确认最薄弱支柱后，再进入步骤2制定补强计划。

2. **针对最薄弱支柱制定补强计划**
   - 根据诊断结果，为最薄弱的支柱制定30天可执行的补强计划：
     - 支柱一薄弱 → 列出需要补的基础知识清单（C/网络/数据库/OS），每天30分钟读经典教材
     - 支柱二薄弱 → 订阅3个一手信息源，找1个比自己强的技术伙伴定期交流
     - 支柱三薄弱 → 选择1个团队中"应该做但没人做"的事（如代码审查/自动化测试），本周推动落地
     - 支柱四薄弱 → 每周至少编程4小时，每两周给自己做一次技术自评
   - 完成标准: 输出一份包含具体行动和时间节点的补强计划
   - 判停条件: 若用户四个支柱评分都 >= 7，则跳到步骤3做维护计划
   - 输出格式:
     ```
     ## 30天补强计划（最薄弱支柱: [名称]）
     | 周次 | 行动项 | 时间投入 | 完成标志 |
     |------|--------|----------|----------|
     | 第1周 | 1. … 2. … | …小时/天 | … |
     | 第2周 | 1. … 2. … | …小时/天 | … |
     | 第3周 | 1. … 2. … | …小时/天 | … |
     | 第4周 | 1. … 2. … | …小时/天 | … |
     **配合skill**: [如支柱二→tech-learning-sop，支柱三→do-right-things]
     ```

3. **建立"永远编程"的纪律**
   - 确保用户在计划中包含"每周最低编码时间"的承诺，并约定检查点
   - 完成标准: 用户承诺了具体的每周编码时间和检查频率（如"每周至少写4小时代码，每月回顾一次"）
   - 输出格式:
     ```
     ## 永远编程承诺
     - **每周最低编码时间**: [X]小时
     - **编码内容**: [具体项目/开源贡献/技术实验]
     - **检查频率**: 每周/每两周/每月回顾一次
     - **下次回顾日期**: [YYYY-MM-DD]
     ```

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **纯管理问题** — 用户的痛点是团队管理（如招聘、绩效、沟通），而非技术领导力。此时应推荐管理类方法论。
- **已完全脱离技术的管理者** — 如果用户已经5年以上不写代码且不想恢复编码，这个模型的核心前提（"永远编程"）就无法成立，强推会适得其反。
- **非技术团队** — 这个四支柱模型是为技术团队设计的，产品团队、运营团队的管理不适用。

### 作者在书中警告的失败模式

- **不写代码的技术管理者陷阱 (ce14)** — 技术管理者脱离编码一线后，逐渐丧失对技术细节的敏感度，做出的决策脱离实际（过度设计或设计不足），无法赢得技术团队的信任。管理者停止编码后，知识停留在"知道"层面而非"做到"层面，决策质量持续下降。
- **长期妥协陷阱 (ce12)** — 面对团队中不合理的现状，选择持续妥协而非推动改变。妥协一次是策略，但每次都妥协就成了习惯。这直接破坏了"支柱三：坚持做正确的事"。
- **不尊重技术的公司衰退模式 (ce22)** — 公司在取得商业成功后，逐渐让非技术出身的人掌权，技术团队的话语权持续下降。雅虎、微软、苹果的历史都证明了这一点。个人再强的技术领导力，在"不尊重技术"的组织中也难以施展。

### 作者的盲点 / 时代局限

- 四支柱模型隐含了一个高门槛假设：管理者必须同时是优秀的技术专家。但在大型企业中，确实存在完全依赖架构设计和系统思维（而非动手编码）的优秀技术管理者。作者断言"不写代码的人无法胜任技术管理"可能过于绝对。
- "给自己打分"的自评方法容易受Dunning-Kruger效应影响——能力不足的人往往给自己打高分，能力强的人反而打低分。
- 模型基于作者在亚马逊、阿里等顶尖公司的经验，对在中小公司做技术管理的人（可能没有Principal SDE可以交流）适用性需要调整。

### 容易混淆的邻近方法论

- "技术管理"与"技术领导力"的区别：技术管理是职位（Manager/Director/VP），关注资源分配、绩效考核、团队建设。技术领导力是影响力（Principle/Staff/Distinguished Engineer），关注技术方向、质量标准、最佳实践。两者可以重叠，但不是同一件事。

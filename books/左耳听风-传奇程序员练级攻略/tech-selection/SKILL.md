# 技术选型四条件评估法

## R — 原文 (Reading)

> 一项技术要想在业界成功应用并长时间发展，需要满足以下四个条件。1)大公司在使用；2)有一个杀手级应用；3)社区比较活跃；4)有不错的第三方贡献。满足2个条件的技术可选，满足3个的技术一定会火，满足4个的是未来。还应该通过招聘趋势和资本投入做大数据验证。
>
> — 陈皓, 第6章 成长中的问题

---

## I — 方法论骨架 (Interpretation)

这是一个用于评估技术产品/工具是否值得采用的四维 checklist，核心思想是：让市场数据替你做判断，而非凭感觉或舆论。

**四个条件**：
1. **大公司在使用**: 有知名大公司在生产环境中使用，证明技术经过了规模验证
2. **杀手级应用**: 有一个让人"因为想用这个应用而必须用这个技术"的标志性场景
3. **社区活跃度**: GitHub star数、issue响应速度、版本发布频率、中文资料丰富度
4. **第三方贡献**: 不只是官方在维护，有大量第三方库、工具、教程和生态

**分级判断**：
- 满足2个 → 可以选，但要做好备选方案
- 满足3个 → 大概率会火，值得投入学习
- 满足4个 → 行业未来方向，值得重点投入

**补充验证**：用招聘网站的岗位数量趋势和资本市场对该技术方向的投入金额做"大数据验证"，避免被主观判断误导。

## A1 — 书中的应用 (Past Application)

### 案例 1: 2016年创业选择可观测性作为产品方向
- **问题**: 2016年创业时需要选择第一个产品方向，可观测性在国内还无人关注
- **方法论的使用**: 用四条件检验可观测性——大公司使用（Google/SFB等在用）✓；杀手级应用（分布式系统监控是刚需）✓；社区活跃度（国外CNCF生态火热）✓；第三方贡献（Prometheus/OpenTelemetry等生态丰富）✓。满足4个条件=未来
- **结论**: 国内还未关注但国外已火的领域正是最佳切入点
- **结果**: 可观测性后来在国内走热，产品方向验证了"关注国外技术前沿、抢占信息高地"的前瞻性

### 案例 2: 亚马逊用算法而非运营解决问题
- **问题**: 在亚马逊观察到工厂用算法指挥工人干活，而国内公司普遍用运营手段解决问题
- **方法论的使用**: 从技术选型角度看，"用算法解决问题"满足四个条件：大公司（亚马逊自身）✓；杀手级应用（库存预测、路径优化）✓；社区（开源算法生态）✓；第三方贡献（学术界的持续研究）✓
- **结论**: 技术驱动的降本增效是正确方向，应该坚持用技术手段而非人力密集型方式
- **结果**: 这段经历影响了后续创业的技术路线——坚持用技术手段而非运营手段解决问题

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. **项目启动选型** — 新项目需要选择消息队列/数据库/前端框架，团队对候选方案争论不休
2. **技术趋势判断** — 看到一篇"XX技术将取代YY"的文章，想判断其可信度
3. **学习方向选择** — 想学一门新技术但不确定值不值得投入时间（如Rust vs Go vs Zig）
4. **评估是否迁移** — 当前用的技术在走下坡路，犹豫是否迁移到新技术
5. **向团队推荐新技术** — 想说服团队采用某个新技术，需要数据支撑

### 语言信号 (用户的话里出现这些就应激活)

- "A和B哪个更好？"
- "XX技术前景怎么样？"
- "该不该学/用XX技术？"
- "XX会不会取代YY？"
- "我们项目该选哪个方案？"
- "这个技术值不值得投入？"

### 与相邻 skill 的区分

- 与 `do-right-things` 的区别: 本skill是"选哪个"的具体评估工具，用四个可量化维度做比较；do-right-things 是"做不做"的价值判断框架
- 与 `info-source-quality` 的区别: 本skill评估的是技术产品/工具的市场成熟度；info-source-quality 评估的是知识/信息的来源质量
- 与 `tech-learning-sop` 的区别: 本skill用于选型决策（选什么），tech-learning-sop 用于学习已有技术的系统方法（怎么学）

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **列出候选技术并逐条检验四条件**
   - 对每个候选技术，用以下表格逐条检验:

   ```markdown
   ### 技术选型四条件评估

   | 条件 | [技术A] | [技术B] | [技术C] |
   |------|---------|---------|---------|
   | ①大公司使用 | ✓/✗/❓ 证据 | ✓/✗/❓ 证据 | ✓/✗/❓ 证据 |
   | ②杀手级应用 | ✓/✗/❓ 证据 | ✓/✗/❓ 证据 | ✓/✗/❓ 证据 |
   | ③社区活跃度 | ✓/✗/❓ 证据 | ✓/✗/❓ 证据 | ✓/✗/❓ 证据 |
   | ④第三方贡献 | ✓/✗/❓ 证据 | ✓/✗/❓ 证据 | ✓/✗/❓ 证据 |
   | **得分** | **N/4** | **N/4** | **N/4** |
   ```

   - 判停条件: 若某个候选技术连1个条件都不满足，直接排除

2. **做大数据验证**
   - 搜索以下数据维度:
     - **招聘趋势**: 岗位数量是上升/持平/下降？（如Boss直聘/Liepin搜索该技术关键词）
     - **资本投入**: 该技术方向的融资事件和投资金额？（如CB Insights/IT桔子）
     - **人才需求**: 人才市场对该技术的需求量级？
   - 判停条件: 若招聘趋势明显下降且无资本投入，即使满足2-3个条件也建议谨慎

3. **输出分级结论**
   - 按以下模板输出:

   ```markdown
   ### 选型结论

   | 技术 | 条件得分 | 大数据验证 | 综合评级 | 理由 |
   |------|---------|-----------|---------|------|
   | [A] | 4/4 | 上升趋势 | ⭐推荐（未来） | [一句话] |
   | [B] | 3/4 | 持平 | ✅可选（会火） | [一句话] |
   | [C] | 2/4 | 下降趋势 | ⚠️谨慎 | [一句话] |

   **建议**: [综合推荐 + 区分因素（如团队技能匹配度、生态成熟度差异）]
   ```

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- **内部自研技术**: 四条件针对的是开源/公开技术产品，公司内部自研系统不适合用这套标准评估
- **过度细分的工具选择**: 如选择哪个日志库、哪个JSON解析器，这类决策的差别不足以触发四条件评估
- **个人兴趣驱动的学习**: 如果学某个技术纯粹出于兴趣而非生产需要，不需要做市场评估

### 作者在书中警告的失败模式

- **盲目追逐新技术 (ce11)**: 看到每个新技术都想深入学一遍，精力分散，每个都浅尝辄止。四条件评估法的价值正在于帮你过滤掉不值得投入的技术，而非什么都学
- **技术平台锁定 (ce02)**: 将核心竞争力建立在某个特定平台上。即使四条件都满足的技术，也应该学底层原理而非只学API用法，因为平台可能被淘汰
- **迷信标准答案 (ce04)**: 把选型当成"找一个最优解"的数学问题。实际上选型是工程权衡，不存在唯一正确答案

### 作者的盲点 / 时代局限

- 四条件隐含了"大公司=好"的假设，但大公司采用某技术可能只是历史原因或政治妥协，不代表技术本身优秀
- "招聘趋势"在中国市场受政策影响大（如某些技术因政策原因突然需求暴增或暴跌），不能完全反映技术本身的优劣
- 未考虑"组合选型"的场景：很多实际项目中需要多个技术协同工作，单独评估每个技术不够，还需要评估组合的兼容性
- 基于互联网行业的经验，对嵌入式、工业控制等领域的技术选型适用性有限（这些领域的大公司可能不使用开源技术）

### 容易混淆的邻近方法论

- 技术选型 vs 技术学习: 选型是"用不用"，学习是"怎么学"。先用本skill判断值不值得投入，再决定是否深入学习
- 技术选型 vs 架构设计: 选型是"选什么工具"，架构设计是"怎么组合工具"。先选型，再设计
